How the tests work

The testing program lives in the testing/ directory. Every skill is validated with a strict A/B protocol that measures the skill's marginal value, not just whether the agent can do the task.

The A/B protocol

Each skill gets 3 trials (5 for the creator family: create-agent, create-skill, create-tool). Every trial is run twice from the identical starting state:

  • Baseline: the task is run with the skill not loaded.
  • Treatment: the same task is run with the skill loaded via load_skill(name).

Both runs are scored against the same rubric, so the difference between them is the skill's actual contribution.

Scoring rubric

Each skill is scored on 5 criteria, each worth 0 to 2 points, for a maximum of 10 per trial:

  • 0 - criterion failed: missing, wrong, or caused harm.
  • 1 - partially met: present but flawed, inconsistent, or shallow.
  • 2 - fully met: correct, complete, no visible defects.

Pass rule

A skill passes only if all three conditions hold:

  1. Treatment average is at least 2 times the baseline average, and
  2. Treatment average is at least 70% of the maximum (7.0 on a 10-point rubric), and
  3. Both trigger probes pass (positive and negative).

Trigger probes are not scored numerically. The positive probe checks that the skill loads when it should; the negative probe checks that it does not load for a nearby-but-different request. If the numerical rule holds but a probe fails, the verdict is needs refinement; otherwise it is fail.

Reproducible fixtures

Trials run against fixtures committed under testing/fixtures/: seeded diffs, planted bugs, mock contacts, and dirty data. Fixtures are checksummed in SHA256SUMS so any two agents can reproduce the same task seeds and produce comparable records.

The three tiers

The per-skill numbers are easier to read through the framework from the earlier single-model portfolio run, which the report and the pack philosophy reference. Skills fall into three tiers based on how much marginal value they add, and the tier predicts the size of the gap you should expect.

Capability-creation skills

These teach the model to do a job it cannot do at all on its own. Baselines fail outright, so the gaps are the largest: 10 to 20 times.

  • improve
  • create-app
  • plan-learning

Discipline skills

These correct behavior where the baseline acts but acts wrongly. The model attempts the task but makes systematic errors, and the skill supplies the missing discipline. Gaps are 2.5 to 5 times.

  • research
  • resolve-recipient
  • create-skill
  • create-agent
  • create-tool
  • personal-context

Craft-reinforcement skills

These enforce consistency where the baseline is already competent. The model can do the task; the skill makes the output reliably conform to a standard. Gaps are 1 to 2 times.

  • review-code
  • write-code
  • write-drafts
  • humanize-text
  • make-docs
  • make-slides
  • and the other office and media skills

Use this framework to interpret the marginal value in the table above: a small ratio on a craft-reinforcement skill is expected and healthy, while a small ratio on a capability-creation skill is a signal worth investigating.

Key findings

These are the complete findings from the report, sections 1 through 7. We report the failures plainly: they are what demonstrate that the testing program works.

1. The 2× marginal-value rule was never met

Every skill and profile combination failed the pass rule. The closest was review-code on gemini-2.5-flash-lite, with a ratio of 1.91 and a needs-refinement verdict, landing at exactly 70% of the maximum. No skill cleared the 2× bar on any profile in this run.

2. Strong models get zero marginal value (ceiling effect)

gemini-3.6-flash and glm-5.3-flash score 7 to 10 out of 10 on their baselines without any skill. The skill adds form (severity grouping, verdicts, structure) but no new findings. The strongest models find the same bugs, write the same drafts, and build the same tools with or without skill instructions. Skills are not a substitute for a strong model.

3. Weak models show the largest skill benefit

This confirms the core hypothesis. gemini-2.5-flash-lite baselines hallucinate APIs, invent findings, and miss planted bugs. On the smallest and cheapest profile, the gains were largest:

  • review-code: 3.67 to 7.0 (ratio 1.91) - the skill nearly doubles review quality
  • research: 5.0 to 7.33 (ratio 1.47) - the skill gets the model to answer at all
  • humanize-text: 5.0 to 6.67 (ratio 1.33) - register preservation
  • plan-learning: 4.33 to 5.0 (ratio 1.15) - structure helps, but the model cannot always sustain it

5. Two skills actively made things worse

In specific contexts, skills hurt rather than helped, and both findings drove fixes.

review-security hurt precision. The skill's thoroughness pressure inflated severities and failed to teach diff attribution. On deepseek-v4-flash the ratio was 0.48, meaning the treatment was worse than baseline: the baseline correctly said "clean diff" while the treatment attributed a pre-existing IDOR to the diff as Critical. All profiles shared the same failure of attributing pre-existing gaps to the diff under review.

research hurt helpfulness offline. The deepseek profile had no web access. Baselines answered from training knowledge with honest caveats; treatments hard-stopped per the skill's rule ("if you cannot find a source, say so and stop"), refusing to answer at all. The ratio was 0.45, treatment much worse than baseline. The skill needed an offline fallback: answer from training knowledge with clear dating and staleness markers.

6. flash-lite reliability findings

gemini-2.5-flash-lite was the least reliable profile, and the findings are specific:

  • Tool use is unreliable for edit tasks: hallucinated reports (claimed edits never made), destroyed a fixture file (overwrote it with invented placeholder code), and claimed test passes against unmodified code. Every claimed edit requires disk verification.
  • Output instability: empty responses, self-duplicated output, and "tool not found" refusals.
  • Provider instability: rate limits and provider errors increased over the session; 7 skills plus 1 partial could not be completed.
  • Review tasks work, edit tasks are dangerous: the model reads code reliably but fabricates when it edits.
  • flash-lite treats skills as tools: briefs must say "Do not load or call any tool or skill."

7. gpt-oss-20b was excluded

gpt-oss-20b could not produce independent repeated runs: it returned byte-identical output across 6 passes even after think:false and num_predict adjustments. This is a model limitation, not a configuration issue, so the profile was excluded from the results. The full reasoning is documented in EXCLUDED-README.md.

A related note: gpt-6.1-sol was skipped entirely because of persistent upstream rate limits on a new, high-demand model. Zero skills were tested on it.

What changed because of testing

The findings fed directly into the catalog. Six skills were refined in commit 2112038, and two were removed.

Six skills refined (commit 2112038)

Skill Refinement
review-securityDiff-attribution rule and clean-verdict permission
review-codeContract-mismatch item added to the priority list
plan-learningAlways-deliver rule: cut scope, never refuse
researchOffline fallback: answer from training knowledge with staleness markers
make-slidesEdit-consistency rule: update all references to changed data
resolve-recipientNo-invented-specifics rule in message bodies

Two skills removed (v0.2.0)

review-security was removed because its core premise did not hold for any model tested. The two failure modes (diff attribution and severity inflation) were fixed and the refined skill was retested, but the average improvement across all four models remained negative at -9%. Modern models already perform security review adequately as part of a general correctness review, and the dedicated prompt encouraged finding-theater over precision.

simplify-code was removed because it provided zero measurable value. On three of four models the baseline and treatment produced identical output, since those models already simplify code correctly. On gemini-2.5-flash-lite the treatment hallucinated its entire output, making the comparison invalid. The four-pass methodology is sound, but it describes what capable models already do naturally.

Full reasoning and the criteria for re-adding either skill: skills/REJECTED.md on GitHub.
